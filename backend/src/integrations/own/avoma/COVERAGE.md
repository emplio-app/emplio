# Avoma coverage

Source: Avoma's OpenAPI spec (dev.avoma.com/openapi.yml with its openapi/components/external.yml), read 2026-11-24 and
generated by `bun scripts/openapi-actions.ts avoma`. Every operation is an action (54), plus next_page by hand. Not
run against a real Avoma account yet: every call and webhook is tested with fetch faked.

Composio's Avoma toolkit has 16 tools and no triggers. All 16 names are kept except list_configuration_resources,
which is covered by list_meeting_types, list_meeting_outcomes, list_templates, list_custom_categories and
list_smart_categories.

## Deliberately left out

| What | Why |
| --- | --- |
| POST /v1/webhooks/ainote/, meeting_booked_via_scheduler*, new_conversation | Not calls: the spec uses them to show what Avoma sends to a webhook |
| Zapier webhooks (target_type 1, new_conversation) | Meant for Zapier; the organization webhook AINOTE is the same event |
| A per-automation team filter | Avoma's `teams` filter is per subscription, and subscriptions are shared by every automation on the event; the organizer_email filter is applied on our side instead |

## Hand adjustments (scripts/openapi/avoma.ts, own/avoma/index.ts)

- Most operations have no operationId: named from a table, Composio's names where it has the call.
- GET v1/revenue_intel/timeline/ lacks its leading slash in the spec: fixed.
- The spec's schemas are in a second file: merged in before generating.
- get_webhook_signing_secret is a GET that shows a secret, so it asks first.
- list_users and get_user have no description in the spec: written by hand.
- next_page (hand-written): Avoma's lists page with a full `next` link; this follows it (only on api.avoma.com).

| Method | Status |
| --- | --- |
| API key (an admin: Settings → Organization → Developer → Add API Key), the whole CLIENT_KEY:CLIENT_SECRET sent as Bearer | done |
| OAuth | Avoma offers none for its API |

Avoma's docs show `Authorization: Bearer <YOUR API KEY>` and say the key is the CLIENT_KEY:CLIENT_SECRET pair; that
the pair goes as one Bearer value is the reading of those two pages, not yet confirmed with a real key.

## Triggers (all by webhook)

| Trigger | Avoma event |
| --- | --- |
| notes_ready | AINOTE |
| meeting_booked | MEETING_BOOKED_VIA_SCHEDULER |
| booking_canceled | MEETING_BOOKED_VIA_SCHEDULER_CANCELED |
| booking_rescheduled | MEETING_BOOKED_VIA_SCHEDULER_RESCHEDULED |

Avoma's subscriptions are one event each, organization-wide, so each event gets its own at
/webhooks/app/avoma/<connection>/<EVENT>, found by address before one is made and deleted (deactivated) by stop.
Avoma signs with one secret per organization (X-Avoma-Signature, HMAC-SHA256 hex of the body). If the organization has
none, ours is set (an HMAC of ENCRYPTION_KEY and the connection, never stored); if it has one already, it's kept and
deliveries are checked against it, read through the key. Unsigned deliveries are refused. Someone calling
set/clear/rotate_webhook_signing_secret later breaks checking only until the next delivery reads the new secret; a
cleared secret stops deliveries passing until an automation is saved again. Avoma sends no delivery id, so a retry is
recognised by its body. Filter: organizer_email. The AI notes' HTML copy is dropped from events (the text copy stays).

Nothing is polled: the API has no other changes to list beyond what the webhooks report.
