(`scripts/openapi/godaddy.ts` says how each part is read):

## Deliberately left out

| What | Why |
| --- | --- |
| Five old Certificates v2 calls (GET /v2/certificates, /v2/certificates/download, /v2/certificates/subscription/{guid}, /v2/certificates/subscriptions/search, GET /v2/customers/{id}/certificates) | In the archived spec but dropped from GoDaddy's current reference; the current subscription/credit searches replace them |
| Parking spec | Never archived; built from the two reference pages instead |
| Domains v2 notification queue as a trigger | GoDaddy hands out one notification at a time until it is acknowledged; polling it would mean acknowledging (taking it from anything else reading the queue). Readable and acknowledgeable as actions (v2_get_next_notification, v2_acknowledge_notification) |
| Certificate, mailbox and hosting-app triggers | Their list shapes aren't documented well enough to compare safely (no tested response); domain, DNS, order, subscription and store-order triggers cover the account's events. Add certificate_issued once a real account shows the shape |
| OAuth sign-in | GoDaddy's third-party sign-in ("Platform Applications") is only for Commerce apps that other merchants install, needs GoDaddy's partner onboarding, and documents no authorize/token URLs. A business connecting its own account uses a PAT, which is GoDaddy's recommendation |
| Webhooks | GoDaddy offers none to account holders; certificates' per-order callback URL (certificate_callback_replace) is an action, not wired as a trigger |
| OTE (test environment) | Production only, as asked |

## Hand adjustments

- **Two logins in one field.** A Personal Access Token (Bearer) and/or the classic `KEY:SECRET` (sso-key), separated by a
  space. Domains v3, Hosting, Email, Shopping, Commerce and ANS take only the PAT; Auctions only the classic key;
  Certificates, Abuse, Agreements, Countries, Orders, Subscriptions, Aftermarket and Parking are documented with the
  classic key, so it goes first there; everything else uses the PAT first. A PAT refused by a classic-key API isn't
  treated as a dead login: the error says to add the key.
- `Idempotency-Key`, `Request-Id` and `X-Request-Id` are filled with a fresh UUID when not given; Orders and
  Subscriptions get `X-App-Key: emplio`.
- Hosting's PATCH bodies are sent as `application/json-patch+json`.
- `{domain-name}` path params are renamed `domain_name` (own/openapi.ts fills word-only names).
- Domain details (`v1_list_domains`, `v1_get_domain`, `v2_get_domain`) hide the transfer code; `get_domain_auth_code`
  (hand-written, asks first) returns it.
- Commerce GraphQL answers errors with a 200: those fail.
- Header defaults that are prose in the archived specs ("Default locale for shopper account") are dropped.
- Names: Domains v3 (GoDaddy's recommended API) has the plain names (`list_domains`, `create_dns_record`); v1 and v2 are
  prefixed `v1_` / `v2_`.
- Lookups that are POSTs run without asking: availability checks, quotes, validations, shopping catalog search,
  ANS resolve/search.
- Asks first even though it's a GET: `certificate_get_acme_external_account_binding` (an ACME account key).

## Auth

| Method | Status |
| --- | --- |
| Personal Access Token (developer.godaddy.com/personal-access-token), Bearer | done |
| Classic key:secret, production (classic-developer.godaddy.com/keys), sso-key | done |
| OAuth (Platform Applications) | not built: see above |

Account rules GoDaddy applies whatever the login: domain management needs the account to hold a domain (or a plan
granting API access); anything that costs money needs a payment profile or Good as Gold balance. Abuse needs onboarding
(abuseapisupport@godaddy.com); Aftermarket expiry listings are for allow-listed registrar partners.
